# TypeScript 服务运行、升级与回退

新服务默认监听 `127.0.0.1:9989`，使用独立的 `data/typescript/` 数据目录。已接入管理员鉴权、多 Bot、WS/HTTP/Debug、任务与执行账本、NapCat 管理、扫码、控制台和新版 UI。默认 Docker 已包含新服务、NapCat 和 Linux QQ，并实测显示真实二维码、重启和备份恢复；真实账号收发与多日稳定性仍需按验证记录验收。默认不启用自动调度。

## 安装与运行

固定使用 Node.js **24.21.0**。Windows、WSL、容器分别安装依赖，不共用 `node_modules`；WSL 创建的工作区符号链接不能直接供 Windows Node 使用。统一使用根目录 `package-lock.json`，原 `web-ui/package-lock.json` 仅保留供旧发布流程回退。

在仓库根目录执行：

```bash
npm ci
npm run verify
npm run start:server
```

`verify` 执行服务端类型检查、行为测试、生产构建，以及前端 lint、类型检查、构建与部署。`start:server` 运行编译后的代码；前端默认从 `web-ui/dist/` 提供。没有前端产物时仍可启动 API。开发后端可使用 `npm run dev:server`。

前端继续使用 hash 路由。修改 `web-ui/` 后必须执行 `npm --prefix web-ui run deploy:full`，由复制脚本更新 Java 回退版使用的 `src/resources/web/`；不能手改该目录。

| 环境变量 | 默认值 | 含义 |
|---|---|---|
| `DATA_DIR` | 项目内 `data/typescript/` | 配置、密钥、任务、账本、保存实例和日志的统一位置 |
| `HOST` | `127.0.0.1` | HTTP 监听地址 |
| `PORT` | `9989` | 预演端口；正式切换时可设置为 `9988` |
| `STATIC_DIR` | 项目内 `web-ui/dist/` | 前端产物目录 |
| `SCHEDULING_ENABLED` | `false` | 是否运行自动任务循环；手动测试仍可发送 |
| `TZ` | `Asia/Shanghai` | 任务时区，切换前应与旧环境核对 |
| `NAPCAT_MODE` | `managed` | `managed` 托管进程，`external` 不管理外部进程，可登记 WebUI 凭据进行扫码代理 |
| `NTP_ENABLED` | `true` | 自动调度启用时进行异步 SNTP 校时 |
| `NTP_SERVERS` | 内置后备服务器 | 可选的逗号分隔校时服务器列表 |
| `NAPCAT_DIR` | 未设置 | 容器默认 NapCat 安装目录；仅补齐尚未配置的值 |
| `NAPCAT_WORK_ROOT` | 数据目录内 `napcat-instances/` | 首次配置的实例工作根目录 |
| `NAPCAT_AUTOSTART` | `false`，默认镜像为 `true` | 启动时恢复保存的托管实例 |
| `CONSOLE_ENABLED` | 交互终端启用 | 可设 `true` 启用管道命令，容器无需开启 |
| `QQ_PATH` | 自动查找 | Windows QQ.exe 或 Linux 已注入 NapCat 的 QQ 明确路径 |

Bash 中启用预演调度：

```bash
SCHEDULING_ENABLED=true DATA_DIR=/绝对路径/预演数据 npm run start:server
```

PowerShell 中对应写法：

```powershell
$env:SCHEDULING_ENABLED = 'true'
$env:DATA_DIR = 'C:\预演数据'
npm run start:server
```

启用调度前先检查导入数据和账号。新旧服务不能同时调度同一 Bot。`/health` 返回实际的 `scheduling` 开关及任务时区。进程不依赖交互式标准输入，可通过 Web 控制台管理；SIGINT/SIGTERM 会关闭调度器、托管进程、连接并释放数据锁。

## NapCat 模式

- Windows 托管需要有效的 NapCat Windows 启动器、DLL 和 QQ.exe。
- WSL 托管需要 Linux NapCat/QQ。不要从 WSL 用 Linux 进程组管理 Windows NapCat；可改在 Windows 原生 Node 中托管，或使用外部模式连接。
- 默认 Docker 为托管模式，QQ 与 NapCat 均在同容器。每个实例具有独立账号目录、虚拟显示、配置和凭据。
- 外部模式拒绝进程启停。可以在管理页面登记 WebUI 地址和 Token，由后台代理认证、状态、二维码与刷新；不要求共享磁盘。凭据加密保存，恢复服务后无需重新登记。
- 服务只停止自己创建的进程树或进程组；保存文件不记录可恢复的进程控制权，重启不依据旧 PID 杀进程。自动停止会检查其他已连接 Bot 对共享实例的使用。

## 导入旧数据

停止旧服务写入，并制作完整备份。导入器保存所选配置、密钥、任务与账本的原字节副本。完整数据、日志及 NapCat 账号目录的备份恢复使用 `backup:data` / `restore:data`，详见「单容器部署」。

```bash
npm run import:legacy -- --source /旧数据副本 --destination /独立新目录 --check --timezone Asia/Shanghai
npm run import:legacy -- --source /旧数据副本 --destination /独立新目录 --timezone Asia/Shanghai
```

先执行仅检查模式，只允许空目标目录。`legacy-backup/` 保存选定源文件原字节，`migration.json` 记录逐文件 SHA-256、时区和限制。导入不启动实例、不启用调度。支持旧单 Bot、`accessToken`、明文和 `RSA:` Token、旧 BCrypt 密码及 Base64 密钥；管理员需重新登录。

坏 JSON、缺失 RSA 密钥、未知账本版本、不安全整数和符号链接会阻止导入。数据目录采用系统独占锁（Linux `flock`、Windows PowerShell 文件共享锁）和版本标记；新版服务异常退出后可自动回收标记并恢复。`.writer.guard` 是持久锁文件，不要在运行时删除。无法识别的旧版标记或跨平台残留仍需确认所有旧服务已退出，再人工移除 `.writer.lock`。存在 `.transaction.json` 时应先启动新服务完成恢复，不能跳过事务直接导出。

## 调度与兼容说明

任务默认使用每日 `HH:mm` 时间和上海时区。默认提前四分钟预热，连接失败每三分钟重试，最多两次；同日启动补发窗口为二十三小时。发送前写入 `SENDING`，成功记录 `SUCCESS`，明确失败记录 `FAILED`，超时或恢复中的发送记录为 `UNKNOWN`。成功及未决目标不自动重投；手动测试也复用当天账本。

自动连接先等待端口就绪，最多 120 秒，再等待 `get_status().online=true`，最多 30 秒；已有连接仍会核对在线状态，超时按连接失败重试，不把离线消息当作已发送。关闭服务会取消等待。同一 Bot 的自动与手动任务串行执行，不同 Bot 独立运行。断开连接不会关闭调度器。自动停止在独立异步工作中执行，受未决滞留、预热、待重试任务、连接代次及共享实例使用关系保护。账本按十四天策略在启动及跨日运行时清理。

Bot 重命名、删除和清空通过带恢复日志的多文件事务联动任务与账本。删除时归档旧任务，避免新建同名 Bot 自动复用。`state`、`state_` 开头的 Bot 名称会与旧任务账本文件命名冲突，拒绝创建。

管理 API 保留 `/api` 和 `ok/data/error` 包裹。参数类型严格检查；消息结果未决返回 504。OneBot 标识符要求安全整数，协议原本使用字符串的参数继续转换为字符串。HTTP 不接收事件，WebSocket 提供每 Bot 独立的处理器链，默认不注册消息命令处理器。

控制台保留业务命令和别名。本机终端支持 `/quit`、`/web start [端口]`、`/web stop`，以及 `/napcat attach <名称>` / `/napcat detach` 的实时日志订阅。停止 Web 期间控制台、Bot 与调度器继续运行，可从终端重新开启监听。Web 端 `/quit` 不退出服务，`/web stop` 提示使用终端，`attach/detach` 显示日志快照及日志页面入口。

OneBot 的 166 个调用签名对照实际 Java 请求夹具；所有具名模型的缺省值、空值、数字与字符串转换、布尔兼容和嵌套 Sender 对照实际 Java 夹具。通用 `callApi` 保持 Java Map 包裹，`callApiRaw` 保留原始数组或空值。超出 JavaScript 安全整数范围的号码仍明确拒绝，避免静默丢失精度。

## Docker 与系统服务

默认部署使用同容器方案：

```bash
docker compose up -d --build
```

详见 [单容器部署](单容器部署.md)。默认新卷与 Java 旧卷分开，调度默认关闭。`Dockerfile.typescript` / `compose.typescript.yml` 保留轻量外部模式，默认预演端口 `9989`；Java 回退文件为 `Dockerfile.java` / `compose.java.yml`。

本机 Linux 可采用 `deploy/qqbot-fire.service` 模板。先安装固定版本 Node、构建项目，为 `qqbot` 用户准备 `/var/lib/qqbot-fire`，核对模板中的 `WorkingDirectory`、Node 绝对路径和 NapCat 安装路径，再安装服务单元。配置覆盖项可写入 `/etc/qqbot-fire.env`。

`fire-stop.sh` / `fire-restart.sh` 默认管理 `qqbot-fire.service`；设置 `FIRE_DEPLOYMENT=docker` 后管理当前 Compose 部署。脚本不再按通用进程名清理整台机器上的 QQ 或 Xvfb，进程清理由所属服务和容器负责。

```bash
FIRE_DEPLOYMENT=docker bash scripts/fire-restart.sh
FIRE_DEPLOYMENT=docker bash scripts/fire-stop.sh
```

## 回退导出

回退必须保留切换后新发送的记录，不能直接恢复旧快照再启用补发。停止新旧服务及自动重启后，将新数据与最终旧数据副本合并到独立空目录：

```bash
npm run export:rollback -- --source /已停止的新数据 --legacy /最终旧数据副本 --destination /空回退目录
```

导出使用新服务的最终配置、任务及密钥，合并同名 Bot 的旧账本；任一侧成功则保留成功，任一侧未决或发送中则保持未决。源目录不被覆盖，`rollback.json` 标记导出完成。删除及重命名后的 Bot 以最终配置为准，不复活已删除对象。

先核对回退目录、任务、时区、NapCat 路径和账号，再让 Java 在此副本中启动。未决目标需人工核对实际 QQ 记录。自动化测试及实际 Java 调度器已验证成功、未决目标不会因回退再次发送；这不替代真实账号和部署环境的完整演练。Java 回退包至少保留七天及完整任务周期，达到稳定标准后再另行清理。
